## Findings

Details are in the [results page](../../../../milestones/m1-050-load-test-results.md).

1. **Condition 2 fails at the agreed limit.** At 8 readers: HTTP p99 2,461 ms (limit 1 s), loop p99
   956 ms (limit 200 ms), 12 of 59 saves; 0 errors. Even demo content alone fails the loop limit and
   the saves at 8 constant readers.
2. **Cause: the adapter's queries.** db-connect 1.1.0 (latest) adds an array branch to every
   equality and `$in` condition, so SQLite cannot use the existing indexes and each of the 11 queries
   per page scans `aposDocs` (14–50 ms each, against 0.01–0.15 ms with the index). Not Litestream,
   and at this size not the menu.
3. **With a measurement-only patch** (scalar core fields skip the array branch): requests about 3.5
   times faster, about 3 times the throughput; at 8 readers HTTP p99 677 ms passes, while loop p99
   342 ms and 36 of 59 saves still fail; at 1 and 2 readers everything passes.
4. **What remains** after the patch: the menu's two-level query on inner pages (about 21 ms), Node work
   turning rows into docs, and the `historicUrls` scan on 404 pages.
5. **Upstream issue drafted** (results §5). Not filed.
