## Change

- **`docker/staging/Dockerfile`:** removes `gosu`, the `mongo` image's `docker-entrypoint.sh`, its
  `js-yaml` and the `esbuild` binaries, then copies the result into one layer on `FROM scratch`.
  Settings that would otherwise be lost are declared again: `HOME`, `GLIBC_TUNABLES`,
  `APOS_RELEASE_ID`, the volumes, the health check and the entrypoint.
- **`docker/staging/run-as.sh`** (new): runs a command as another user with `setpriv`, which the base
  image already has. It sets `HOME` as `gosu` did, and uses `exec` to keep the process ID.
- **`entrypoint.sh`, `pbmc.sh`:** use that wrapper. The behaviour is otherwise unchanged.
- **Runbooks:** results added to the [staging container](../../../../runbooks/staging-container.md)
  and [PBM](../../../../runbooks/pbm-backup-and-restore.md) runbooks.
- **Unchanged:** the root `Dockerfile`, the demo image and `docker/pbm-poc/` keep `gosu` and `esbuild`.
  D-SEC-8 covers the staging image only.

**Added beyond the handoff's wording, and adjustable:** removing `js-yaml` and the entrypoint (the
scan showed that only the entrypoint used `js-yaml`), and the single layer.

## Findings

1. **Deleting a file in a later Docker layer does not remove it from the image.** With `rm` alone, the
   files were gone from the running container, but the scan still listed all 78 findings, at the
   same paths. The bytes stay in the inherited layers. Only the single-layer image cleared them.
2. **Scan of the site image, Docker Scout, critical and high only:**

   | Image | Critical + high findings |
   |---|---|
   | m1-055 layout, also with files only deleted | 78 (8 critical) |
   | **Single layer** | **7 (0 critical)** |

   The 7, all high and **none accepted**:

   | Package | Where | Fix listed | State |
   |---|---|---|---|
   | `go-jose` 4.1.5, `klauspost/compress` 1.20.1, `x/net` 0.60.0 | `pbm`, `pbm-agent` | yes, upstream | Accepted until a fix (D-SEC-5). `v2.17.0` is still Percona's latest release |
   | `x/net` 0.61.0 | `mongodump`, `bsondump` | 0.62.0 | Kept: these tools are the fallback in D-DB-12 option C. For the owner |
   | `apt` 2.8.3 | base image | 2.8.4ubuntu0.1 | Not used by the running site. For the owner: upgrade it, or take a newer `mongo` digest (a new image needs approval) |
   | `async` 0.9.2, 1.5.2 (CVE-2021-43138) | app dependencies, one through `uploadfs` | 2.6.4 | Not investigated |

   **Reachability was not analysed**, so this is no statement that they are safe. nginx (2 high) and
   certbot (13 high) were rescanned without a rebuild, with the same counts as m1-055.
3. **Costs of the single layer.** An image shares no layers with the base, so each release transfers
   the whole image. The `mongo` image's settings must be kept in step by hand; a comment in the
   Dockerfile says so. A release that sets `APOS_RELEASE_ID` must pass the same value to both
   builds. The image shrank from 2.59 GB to 2.34 GB.
4. **The Chrome extension cannot operate the certificate warning page** (screenshots, keys, page
   reading and scripts all fail), so the owner clicked through it. Chrome keeps that exception for a
   while. The system trust store was not changed.
5. **Memory on this PC blocks the rest.** The runbook's `$S build` took available memory down to
   382 MB. Docker's VM still held about 6 GB after the build ended, and available memory was back at about 5.5 GB some minutes later. See the next section.
