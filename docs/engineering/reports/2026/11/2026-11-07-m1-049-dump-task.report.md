## Findings

Details are in the [results page](../../../../milestones/m1-049-dump-task-results.md).

1. **The task works.** Its file equals `apos-db-dump`'s file without the stray `_litestream_seq` line
   (byte for byte), exits with 0, and restores into a new, empty file with identical rows and indexes.
   The restored copy starts as a site and passes smoke 18/18.
2. **The app's own connection is the wrong one to dump from.** The first version used `self.apos.db`.
   Its dump had other index names, and a restore lost 3 of 30 indexes because SQLite index names are
   database-wide. The task now opens a new connection through Apostrophe's `connectToAdapter()`. A
   unit test covers it.
3. **Point 4 confirmed.** `apos-db-restore` of a dump with the stray header creates `_litestream_seq`
   as a collection table. Litestream's checkpoints then fail with errors and growing back-off while
   `litestream status` reports `ok`; the WAL is not checkpointed and replication is delayed. m1-048 did
   not see this because nothing triggered a checkpoint. Any restore from an old `apos-db-dump` file
   needs this in mind.
4. **Upstream issue drafted** (results §5), with the index-name point as a side note. Not filed.
