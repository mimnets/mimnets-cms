## Findings

Details are in the [results page](../../../../milestones/m1-046-pbm-poc-results.md).

- **PITR restore works.** A restore to 11:38:20Z into a new, empty container brought back a test piece
  archived at 11:38:37Z, and none of the 15 pieces written after the target. All suites passed on the
  restored site.
- **Credentials in plain text.** With S3 storage, `admin.pbmConfig` holds the access key, secret key
  and SSE-C key in plain text, and every backup contains `admin.pbmConfig`. `pbm config --list` masks
  them. This weakens the SSE-C plan in options paper §4.3.
- **RPO depends on the base backup.** Slicing pauses during a base backup, so the RPO is about one
  slice plus the backup duration. The largest lag seen was 666 s (11.1 min).
- **Three high findings** in PBM's libraries, all denial of service, no fixed release (D-SEC-5).
- **A restore needs the source's database secrets,** because the backup contains the database users.
  The staging design needs a secret store that survives the server.
- **Cross-building for `arm64` needs the `build-only` Compose profile.** Otherwise Compose builds the
  base for the host's platform.
- **The demo image passes `ASSURER_ADMIN_PASSWORD` into the app's environment.** Not from PBM; the
  staging image should not.

## Security observations

- PBM keeps storage credentials and the SSE-C key in plain text in the database, and in its backups
  (results §3.2). Possible mitigations, none tested: PBM's Vault support, bucket-scoped credentials with
  object lock, and treating every backup as a secret.
- Root in the container can read the PBM credentials. The separate OS user protects only against an
  app compromise (options paper §4.1).
- Each backup holds the SCRAM hashes of all database users.
- A fake S3 configuration with dummy values was set on the disposable restore container to check P8.
  Nothing was sent anywhere: the endpoint was `127.0.0.1:9`, where nothing listens.
