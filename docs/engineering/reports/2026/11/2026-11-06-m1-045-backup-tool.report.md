## Findings

Details and sources are in the [options paper](../../../../milestones/m1-045-backup-tool-options.md).

- **PBM conflicts with two written rules.** Runbook §6 plans a `backup` role, and PBM needs `anyAction`.
  Backup protection plan §2 asks for write-only credentials, and PBM needs delete rights. The
  mitigation for the second, object lock, is not tested.
- **Encryption has a possible trap.** Hetzner has no default encryption, so backups depend on SSE-C. The
  `minio` type, PBM's documented fallback for S3 errors, has no SSE-C setting in its reference.
- **Only logical backups work on Community,** so restores are slower and R3 has to be measured.
- **PBM does not schedule itself,** and its failure would not show on the planned uptime check. The RPO
  needs an alert on backup status, and no alert service is chosen.

## Security observations

- A PBM user with `anyAction` in the same container as the app increases the damage from a container
  compromise. A separate OS user limits an app compromise only. To be checked in the proof of concept
  (P7).
- Whether PBM's configuration exposes the storage credentials or SSE-C key in `admin.pbmConfig`, its
  output, its logs or a backup is **not verified** (P8).
- Backups hold password hashes, sessions and personal data (backup protection plan §1), so an S3 test
  must use disposable data only.
