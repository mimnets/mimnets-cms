## What was built

| Item | Implementation |
|---|---|
| Global Styles: admins only | `modules/@apostrophecms/styles/index.js`: core options `editRole: 'admin'` and `publishRole: 'admin'` (core default is `editor`; `@apostrophecms/user` uses the same pattern). Enforced by `apos.permission.can()` and its query criteria, so the REST API refuses an editor's write, the palette icon (admin bar item, permission `edit`) is hidden and the `T,P` command does nothing. `viewRole` is unchanged: the styles are served to every visitor as CSS, so an editor can still read the document |
| Admin bar menus | New `modules/@apostrophecms/admin-bar/index.js`: core `groups` option. Content (Products, Organizations, People, Locations), Media (Images, Image Tags, Files, File Tags), Forms (one item, so a plain button), Site admin (Users, Redirects). Pages (the page tree) stays first, outside the groups. Labels in `project:` i18n (`adminBarContent`, `adminBarMedia`, `adminBarForms`, `adminBarSiteAdmin`) |
| Tests | `scripts/content-model-test.mjs` (run by `test:ci`): admin reads the styles document; editor PATCH refused; styles unchanged after the attempt; admin can still save |

**Differences from the handoff plan:**

- The handoff expected a **403** for the editor's write. Core answers **404**: when a document is
  outside the user's edit criteria it is reported as not found. The write is refused and nothing
  changes; the test accepts 401, 403 or 404, as the suite's other permission checks do.
- An editor cannot see Users, so the Site admin group has one visible item for editors and core
  shows it as a plain **Redirects** button, not a menu. Owner shown; layout approved as is.
